# 压测报告

压测在 GitHub Actions 上运行（`.github/workflows/perf.yml`），推送到 `perf/**` 分支或手动触发，结果以 Job 注解形式输出。这些数字来自 GitHub Actions 的共享机器，只反映相对量级，不代表任何学校服务器上的实测性能。资源限制与开发编排中的限制一致：应用 2 核 4G、MySQL 2 核 2G、Redis 1 核 512M。

标题中的 M7、M8 是验证指标编号，含义见设计文档“验证”一节。多个收费窗口同时挂同一号源不会超挂，由集成测试 `BookingConcurrencyTest` 验证（1200 个并发请求抢 50 个号，成功恰好 50）。

## M7 日常收费 10 倍峰值

**规模假设**：按单个校医院门诊日均约 150 人次、8 小时、高峰时段集中 3 倍估算，峰值约 1 笔/秒，10 倍为 10 笔/秒。该人次是压测用的假设值，部署前应按本校实际门诊量调整。

**场景**（`perf/k6/charge.js`）：收费员登录后循环“按学号检索患者 → 划价生成收费单 → 窗口结算（带幂等键）”，10 笔/秒恒定 10 分钟，第 4 分钟起叠加 50 笔/秒持续 1 分钟。后台同时运行发件箱投递等定时任务。

**结果（2026-10-26）**：外部平台全部未接入，与部署后的初始状态一致。有医保报销的单登记医保终端的结算单号和统筹金额后收现金。

## M8 150 万条资金流水的月报

`perf/seed/ledger-1.5m.sql` 在 2026-08 写入 150 万条流水（约 5 万条/天，远高于单个校医院的实际量，用来放大差距）。同一个月报接口分别用两种数据源各查 10 次：

| 数据源 | 中位数 | 最大 |
| --- | --- | --- |
| 直接扫流水（`source=ledger`） | 3,957ms | 4,014ms |
| 每日预聚合 + 当天实时（默认） | **2.5ms** | 2.9ms |

两种数据源的结果逐项相同。预聚合每天凌晨用流水重算前两天；流水只追加、退费记在退费当天，过去的日期不会再变，所以预聚合不会过期。
